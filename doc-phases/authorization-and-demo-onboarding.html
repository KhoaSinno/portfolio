Tài liệu mô tả logic đang chạy trong dự án: Supabase Auth, CMS allowlist, quyền sở hữu CV, public publish, demo account và reset demo. Hãy đọc trước khi sửa authentication, ResumeService hoặc API admin.

Tóm tắt cho fresher

  1. ADMIN_EMAILS quyết định ai được vào CMS.
  2. PORTFOLIO_OWNER_ID quyết định ai là chủ portfolio; đây là Supabase UID, không phải email.
  3. Mọi CV có ownerId. API admin luôn query theo UID đó, vì vậy user không đọc/sửa CV của nhau.
  4. GET /api/resume chỉ phục vụ CV primary + published của chủ portfolio. Demo publish không thể thay đổi homepage.
  5. Demo là workspace showcase dùng chung. Người test có thể thử edit, multi-CV, publish và rollback; owner có nút Reset Demo để seed lại fixture sạch.
Nguyên tắc: UI là trải nghiệm; backend mới là security boundary. Dù user tự gọi API bằng DevTools, server vẫn kiểm tra token và ownerId.

3. Data model: CV thuộc về ai?

Resume: id, ownerId, title, slug (unique), isPrimary, status (DRAFT|PUBLISHED), content (JSON), versions[]
ResumeVersion: resumeId → Resume.id, version, content snapshot
Rule DB: mỗi owner có tối đa một CV primary; một owner vẫn có thể có nhiều CV.
Rule bắt buộc khi viết admin query: dùng where: { id, ownerId } (hoặc where: { ownerId } khi list). Query chỉ theo id là lỗ hổng cross-user.

4. Luồng xác thực và ownership

4.1 Guard chặn từ ngoài vào

// backend/src/auth/supabase-auth.guard.ts — ý nghĩa rút gọn
const token = getBearerToken(request.headers.authorization);
const { data, error } = await client.auth.getUser(token);
if (error || !data.user) throw new UnauthorizedException();
if (!adminEmails.includes(data.user.email.toLowerCase())) throw new ForbiddenException();
request.user = data.user;

Token hợp lệ nhưng email không thuộc ADMIN_EMAILS vẫn nhận 403. Tất cả /api/admin/... trong ResumeController dùng guard này.

4.2 Lần đầu mở CMS: ensurePrimaryResume

  1. Tìm CV theo ownerId. Có rồi thì dùng; nếu chưa có primary thì sửa CV đầu tiên thành primary.
  2. Nếu UID là PORTFOLIO_OWNER_ID và canonical record portfolio-resume tồn tại, gán record đó cho owner. Đây là recovery có kiểm soát cho dữ liệu legacy.
  3. Nếu là demo hoặc admin mới: tạo CV fixture riêng, slug riêng và Version 1 trong transaction.
if (ownerId === portfolioOwnerId && legacyResumeExists) claim canonical portfolio-resume;
else create a new owner-scoped CV + first snapshot;
Không quay lại logic cũ: “không phải demo ⇒ root”. Mọi admin không phải demo sẽ có thể chiếm canonical CV. Root phải luôn so bằng UID cấu hình.

11. Walkthrough code: Backend làm gì?

Luồng NestJS là: Guard xác thực và allowlist → Controller chỉ map route/DTO → Service áp nghiệp vụ/ownership → Prisma query database.

SupabaseAuthGuardJWT + allowlist
→

→
ResumeService / PrismaownerId + transaction

11.1 Guard: authentication khác allowlist

// backend/src/auth/supabase-auth.guard.ts — canActivate()
    const token = getBearerToken(request.headers.authorization);
    const { data, error } = await client.auth.getUser(token);
    if (error || !data.user) throw new UnauthorizedException(); // 401
    if (!adminEmails.includes(data.user.email.toLowerCase())) {
      throw new ForbiddenException();                            // 403
    }
    request.user = data.user;

Token cho biết “ai đang gọi”; ADMIN_EMAILS quyết định “ai được dùng CMS”. Controller chỉ sử dụng UID tin cậy request.user.id, không nhận ownerId từ request body.

11.2 Controller giữ mỏng

// backend/src/resume/resume.controller.ts
    @Get('admin/resumes/:id')
    @UseGuards(SupabaseAuthGuard)
    getResumeById(@Req() req, @Param('id') id) {
      return resumeService.getResumeById(req.user.id, id, req.user.email);
    }
    
    @Post('admin/resumes/:id/publish')
    @UseGuards(SupabaseAuthGuard)
    publishById(@Req() req, @Param('id') id, @Body() dto) {
      return resumeService.publishById(req.user.id, id, dto);
    }

Controller không tự phân biệt demo/owner và không tự query DB. Các legacy route /api/admin/resume vẫn có để tương thích, nhưng resolve primary CV của chính UID caller.

11.3 Câu lệnh ownership bắt buộc

// resume.service.ts — saveDraftById()
    const resume = await prisma.resume.findFirst({
      where: { id, ownerId },
    });
    if (!resume) throw new NotFoundException('Resume not found.');
    return prisma.resume.update({ where: { id }, data: { content } });

Đây là chống cross-account thật sự: demo gửi ID owner thì không tìm thấy record { id, ownerId: demoUid }. Chỉ sau khi xác minh object thuộc owner mới update theo id.

11.4 Publish/rollback và version history

// publishById() — transaction Serializable
    1. find Resume where { id, ownerId }
    2. update content + template + status=PUBLISHED + publishedAt
    3. lấy version lớn nhất
    4. create ResumeVersion(version = latest + 1)
    
    // rollbackVersion()
    1. kiểm tra Resume { id, ownerId }
    2. tìm version where { id: versionId, resumeId: id }
    3. create version mới chứa content cũ
    4. update Resume thành content cũ và PUBLISHED
Nghiệp vụ History: rollback không xóa hay chỉnh version cũ. Nó tạo một snapshot mới, nên audit trail luôn giữ được đường đi của nội dung.

12. Bốn request flow cần thuộc

A. Demo login → CMS

  1. Login page tạo Supabase session.
  2. proxy.ts thấy claims và cho vào editor.
  3. Editor gửi JWT; Guard xác thực + kiểm tra email demo trong allowlist.
  4. listResumes(demoUid) seed nếu cần và query where: { ownerId: demoUid }.

B. Demo publish → homepage không đổi

  1. Publish endpoint chỉ update resume { id, ownerId: demoUid } và snapshot.
  2. Slug demo public được, nhưng canonical endpoint query PORTFOLIO_OWNER_ID.

C. Demo cố gửi owner resume ID

  1. Guard có thể pass vì demo là CMS user hợp lệ.
  2. Service tìm { id: ownerResumeId, ownerId: demoUid } không thấy và trả 404.
  3. Không có dữ liệu owner nào được read/update.

D. Owner Reset Demo

  1. Guard pass, service còn so UID với PORTFOLIO_OWNER_ID.
  2. Server-only service role key tìm UID demo@gmail.com, delete Resume theo đúng UID đó rồi seed fixture Version 1.
  3. Resume owner không khớp điều kiện delete nên an toàn.

13. Khi sửa code, hãy tự hỏi

  3. Logic root có so với PORTFOLIO_OWNER_ID thay vì suy luận từ email/demo không?
